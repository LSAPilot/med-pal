# Deployment (section 4)

Two repos, one direction: development happens only in `med-pal`; the Space clone
`/home/lorenz/medical-app-regulatory-helper` (remote `git@hf.co:spaces/LSAPilot/medical-app-regulatory-helper`) is filled by a script.
Nothing in this document has been pushed or published yet.

## How the app is built
```
app.py (root)                entry point for Spaces and local runs; ZeroGPU marker
src/regulatory_helper/
  app.py                     Gradio UI only (gr.Blocks + gr.Chatbot), no logic
  service.py                 Service.ask(): input check -> cache -> visitor limit -> daily limit -> generate.answer_question
  limits.py                  DailyLimit, VisitorLimit, AnswerCache (in memory, injectable clock)
  generate.py, retrieval.py  unchanged core from sections 2 and 3
data/examples.json           5 example questions x 2 languages with precomputed answers (no API call at runtime)
```
The UI calls exactly one function, `Service.ask(question, history, lang, mode, visitor) -> Reply`. A later custom frontend can call the same function.

## Budget protection (all configurable, defaults in `limits.LimitConfig`)
| Setting | Default | Environment variable (Space *variable*, not secret) |
|---|---|---|
| questions per UTC day, all visitors | 100 | `DAILY_LIMIT` |
| questions per visitor and window | 10 per 3600 s | `VISITOR_LIMIT`, `VISITOR_WINDOW_S` |
| cache size (identical question + language + mode + history) | 500 | `CACHE_SIZE` |
| maximum question length | 500 chars | `MAX_QUESTION_CHARS` |

- Order of checks: input, cache (free, does not count), visitor limit, daily limit, API. A reached limit gives a friendly message and **no API call**.
- Example buttons use precomputed answers and cost nothing. They still enter the conversation history, so follow-ups work.
- Counters and cache live in memory; a restart resets them. The spend limit in the Anthropic Console stays the hard ceiling.
- The per-visitor limit identifies visitors by `X-Forwarded-For` (fallback: client address), reduced to a salted hash that exists only in memory. On Hugging Face this is only roughly reliable (shared proxies, changing addresses).
- A failed API call still counts against both limits (protects against error loops).

## Privacy
Question texts, answers and addresses are never logged or stored. Logged are only counters per request (`outcome`, tokens, cost, cumulative totals) and the exception *type* on errors. Tests check that question text and address do not appear in the log. Gradio telemetry is switched off (`analytics_enabled=False`, `GRADIO_ANALYTICS_ENABLED=False`). The in-memory cache is keyed by hashes. Note: `huggingface_hub`/`httpx` may log request URLs for the model download; these contain no user content.

## Versions
- Local: Python 3.12 (`.python-version`), Gradio 6.31.0 (dependency group `app`) = `sdk_version` of the Space. `uv run python app.py` and the full test suite ran on this combination.
- `requirements.txt` is generated by `uv export --no-dev --no-group app` (Gradio excluded, it comes from `sdk_version`). **Torch differs between local and Space:** locally `uv.lock` pins the CPU build (`torch==2.15.0+cpu` from the PyTorch CPU index, saves ~4.5 GB). ZeroGPU rejects that ("torch version in requirements.txt is not compatible with ZeroGPU"; supported on 2026-11-12: 2.13.0, 2.12.1, 2.11.0, 2.10.0, 2.9.1, 2.8.0). `scripts/build_space.py` therefore removes all `torch` lines and the `--extra-index-url` line from the export and pins `torch==2.13.0` (constant `SPACE_TORCH_VERSION` in the script; change it there if Hugging Face changes the list, then re-sync). `sentence-transformers` 6.3.0 needs `torch>=2.2`, `transformers` `torch>=2.6`; checked in a separate venv with `torch==2.13.0+cpu` and the Space dependencies: embeddings match the stored index (max. deviation 1e-7), search results unchanged.

## ZeroGPU (prepared, not yet tested on the Space)
The Space runs on ZeroGPU hardware. The app needs no GPU.
- A ZeroGPU Space is documented to refuse to start without at least one `@spaces.GPU` function, so root `app.py` registers a marker function if the `spaces` package is importable (preinstalled on ZeroGPU, absent locally and therefore skipped). The function is never called, so no GPU quota is used. This could not be tried locally.
- The embedding model is loaded with `device="cpu"` explicitly (`retrieval.get_model`), so queries never touch the emulated CUDA device outside a GPU function.
- Index and embedding model are loaded at startup (`Service.warm_up`), not on the first question. The model (~130 MB) is downloaded from the Hub on the first start (cold start).
- **To verify after the first build:** (1) the Space starts, (2) a question works. The torch pin is covered above; if Hugging Face changes the supported list, adjust `SPACE_TORCH_VERSION`. Quotas of ZeroGPU were not measurable offline.

## Your manual steps
1. **Refresh and check locally** (in `med-pal`):
   ```bash
   uv run pytest
   uv run regulatory-helper ingest && uv run regulatory-helper index   # only if chunks or model changed
   uv run python scripts/precompute_examples.py                        # only if prompt, model or index changed (costs < 1 cent)
   uv run python app.py                                                # try it at http://127.0.0.1:7860
   ```
2. **Sync into the Space clone** (writes files, runs no git command):
   ```bash
   uv run python scripts/build_space.py --dry-run   # list what would be copied
   uv run python scripts/build_space.py
   ```
   The script refuses to run if the index hash does not match `chunks.jsonl`, if the example sources do not match `chunks.jsonl`, if the Space README lost its YAML header, or if `sdk_version` differs from the pinned Gradio version.
3. **Check the Space clone:**
   ```bash
   cd /home/lorenz/medical-app-regulatory-helper && git status && git diff README.md
   ```
   Expected new files: `app.py`, `.gitignore`, `requirements.txt`, `src/`, `data/` (no `data/raw`, no tests, no `.env`). The README diff must only touch the text below the YAML header.
4. **Check Git LFS before `git add`.** The Space's `.gitattributes` sends `*.npy` through LFS; without it Hugging Face rejects the binary `embeddings.npy` (~4 MB). Git LFS 3.8.1 is installed on this machine (binary in `~/.local/bin/git-lfs`, set up with `git lfs install`). Verify in the Space clone:
   ```bash
   git lfs version
   git check-attr filter -- data/processed/embeddings.npy   # expected: filter: lfs
   git add -A && git lfs ls-files                           # expected: data/processed/embeddings.npy is listed
   ```
   `*.json`/`*.jsonl` are under 10 MB and go through normal git. On a fresh machine: install `git-lfs` (e.g. `sudo apt install git-lfs`) and run `git lfs install` once.
5. **Set the secret before the first start:** Space page -> Settings -> *Variables and secrets* -> **New secret** `ANTHROPIC_API_KEY` (a secret, not a variable, not a file). Optional *variables*: `DAILY_LIMIT`, `VISITOR_LIMIT`.
6. **Commit and push by hand:**
   ```bash
   cd /home/lorenz/medical-app-regulatory-helper
   git add -A && git commit -m "feat: deploy regulatory copilot" && git push
   ```
7. **Watch the build:** Space page -> *Logs* (Build, then Container). Look for the `torch==2.13.0` install and `Running on local URL`. In the container log each question shows up as `request outcome=... tokens=... cost=...` without question text.
8. Ask one question and compare the cost in the Anthropic Console; keep the workspace spend limit low.
